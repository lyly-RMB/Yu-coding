## 3. 核心执行原则

### 3.0 人机分工与发送方式

Cursor 负责读取剧本、指导下一步、观察群聊、判读最终回复、保存截图和写入结果；真实飞书消息由人使用已登录的飞书客户端发送。除非另有已验证的飞书 API 发送器，本轮不得假设 Cursor 可以直接伪造真实 mention。

人工发送时必须从候选菜单点选真正的机器人“飞书”。Cursor 不能仅凭文本 `@飞书` 判定 mention 成功。

本轮的实际方式就是“人工发送、Cursor 执行测试控制和记录”：

- 人：在飞书群输入 `@`，从候选菜单点击“飞书”，补全消息并点击发送；
- Cursor：告诉人下一条应该发什么，观察群聊，等待最终状态，保存截图和结果；
- Cursor 不负责伪造 mention，也不把输入框里的纯文本 `@飞书` 当成真实艾特；
- 人发送完一条后，不要提前准备并发送下一条，等 Cursor 判定本条完成。

### 3.1 一次只发一条

每条消息都必须按以下循环执行：

1. 在飞书群中发送一条消息。
2. 确认机器人收到消息。
3. 忽略“收到，正在回答……”这类中间确认。
4. 等待最终回答、最终错误或超时判定。
5. 保存消息、最终回复、时间、Run ID、Trace ID 和截图。
6. 只有完成第 5 步后，才允许发送下一条。

禁止批量粘贴多条剧本消息。禁止看到“收到，正在回答……”就继续发下一条。

### 3.4 超时数字和处理

超时必须对齐当前 Hermes 流配置（`.env` 中 `HERMES_CODEX_EVENT_STALE_TIMEOUT_SECONDS` / `HERMES_STREAM_READ_TIMEOUT` / `HERMES_STREAM_STALE_TIMEOUT` 均为 300 秒）。观察端不得短于该值，否则会把仍在合法流窗口内的慢答误判为超时。

- 中间 ack 上限：15 秒；15 秒内没有“收到，正在回答……”或等价受理信号，记为 `ack_timeout`（可附 P2），但仍继续等待最终回复，不因仅缺 ack 停剧本；
- 最终回答上限：330 秒（Hermes 300 秒 + 30 秒观察缓冲），从发送消息时开始计算；
- 到达 330 秒仍没有最终回答或明确错误，记为 `timeout`，停止当前剧本；
- 超时后只允许检查一次服务 health/status，并记录状态；不得对同一 sequence 连发重试；
- 只有确认是客户端观察问题且服务端已有最终结果时，才允许人工重新打开群聊查看，不得重新发送消息碰运气。

### 3.2 正确艾特方式

必须在飞书输入框中输入 `@`，从候选菜单中点击真正的机器人 **“飞书”**。不能直接输入纯文本 `@飞书`，不能选择“所有人”，不能选择测试用户。

方式 A 的实际消息格式：

```text
@飞书 /sim <role> <message>
```

本轮所有 `/sim` 消息都必须真正艾特机器人。JSON 中 `feishu_mention_required: false` 只表示该业务发言本身不是“向机器人提问”，不表示可以发送纯群聊文本。纯文本角色消息不会纳入有效回放。

本轮只使用 `/sim <role> <message>`；`/pl-sim ...` 视为兼容别名，不纳入结果记录，禁止混用。

只有剧本中的干预问题使用普通机器人艾特：

```text
@飞书 请总结刚才的讨论。
```

### 3.3 最终回复判定

以下内容都不是最终完成：

- `收到，正在回答……`；
- 预览卡片；
- 输入框中的发送状态；
- 飞书客户端的本地加载动画。

以下内容才算完成：

- 机器人发出完整项目回答卡或完整文本回答；
- 机器人发出明确的 ProjectLens/Hermes 错误消息；
- 达到约定超时后记录为“超时”，并停止当前剧本。

### 5.3 剧本三重点

- 群聊结论先生成记忆提案；

1. 使用真实候选艾特“飞书”发送 `@飞书 /sim developer 批准刚才的项目记忆。`，预期为拒绝或不具备批准权限；

3. 等待最终结果后发送“这个决策现在已经是正式项目事实了吗？依据是什么？”，检查是否保留审批人、时间、来源和内容依据。

如果系统只支持卡片审批而没有可用卡片，记录为功能阻塞，不得用自然语言“批准”代替审批动作。

### 6.1 单条判定规则

- 普通 `/sim`：只判定“是否被正确受理、是否没有串角色、是否最终完成或明确失败”；不单独对全部 acceptance checks 打分；
- `interventions`、结束问题和剧本三 `approval_checks`：必须逐项对照 acceptance checks 判定；
- 全部关键检查通过为 `passed`；有事实错误、角色串线或关键证据缺失为 `failed`；
- 仅格式、引用不完整但结论基本正确，记 `passed_with_defect` 并创建 P2；
- 未完成或被停止不得判为 passed。

## 7. 缺陷记录标准

优先使用 `evaluation/feishu_team_test/defect.template.csv`。

严重级别：

- **P0**：数据泄露、跨项目越权、错误写入正式记忆、服务完全不可用；
- **P1**：核心回答错误、上下文串错角色、最终回答丢失、连续消息导致状态错乱；
- **P2**：证据引用不完整、角色视图不准确、错误恢复体验差；
- **P3**：文案、格式、按钮或非核心体验问题。

缺陷必须包含：复现步骤、输入消息、期望结果、实际结果、消息顺序、Run ID、截图、是否可重复、严重级别。

## 8. 立即停止条件

出现以下任一情况，立即停止当前剧本并记录缺陷：

- 出现跨项目或受限资料泄露；
- 机器人把未审批讨论说成正式事实；
- 机器人最终回复尚未完成就发送下一条；
- 连续两次出现 Hermes/网关错误；
- 出现 `Codex stream produced no SSE events ...` 等流式超时；
- 同一条消息被重复处理且产生重复回答；
- 服务连接状态变为非 `connected`。

停止后的恢复协议：

- P0：停止全部剧本，先修复并重新进行环境预检；
- P1：停止当前剧本，修复后从 `/clear` 重新跑该剧本，不从失败 sequence 续跑；
- P2/P3：可以完成当前剧本，但必须记录缺陷；
- `timeout` 或网关流式错误：停止当前剧本，只允许查一次 status；修复后从 `/clear` 重跑；
- 任何情况下不得通过同一 sequence 连发多次来掩盖抖动。

## 9. 通过标准

### 单剧本通过

- 所有必需消息均按顺序完成；
- 没有 P0/P1 缺陷；
- 最终回答能引用证据并区分未知；
- 角色和上下文没有串错；
- 失败时有明确错误，不静默丢消息。

### 小范围试运行建议通过

- 三个剧本均完成；
- 无 P0；
- P1 为 0，或已有明确修复和回归证据；
- 权限、隔离、记忆审批至少各完成一轮正向和反向验证；
- 连续运行期间没有未解释的消息丢失、重复或跨轮污染。

跨项目/权限隔离、重复消息幂等、服务重启恢复和主动提醒不属于三个核心剧本的充分覆盖项。本轮至少补做以下最小用例并单独标注：

- 询问受限资料或错误项目，预期拒绝且不泄露内容；
- 对同一条消息做一次重复事件/重复发送验证，预期不产生双答；
- 可选重启 API/长连接后再问一条新问题，验证服务恢复；
- 主动提醒能力本轮明确记为“未覆盖”，不得误判为通过。

## 11. 给 Cursor 的执行要求
