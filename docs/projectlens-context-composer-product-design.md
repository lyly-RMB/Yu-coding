# ProjectLens 上下文管理器产品设计

版本：v0.1  
日期：2026-09-20  
文档性质：产品设计说明，不是开发实施方案  
产品入口：飞书互动卡片

## 1. 这是什么

ProjectLens 上下文管理器是一个运行在飞书里的小型可视化工具。它让用户在每次向 Agent 提问前，决定本次 Agent 可以看到哪些内容。

它解决的不是“聊天记录保存”问题，而是“本次 Agent 应该知道什么”问题。

~~~text
今天的聊天记录
+ 用户主动选择的历史内容
+ 用户主动选择的摘要、状态和证据
-> 本次上下文
-> Agent 回答
~~~

一句话定义：

> **上下文管理器是一个按天隔离、按需回溯、带完整性提醒的 Agent 上下文选择器。**

它不是聊天记录删除器，也不是项目状态修改器。用户取消一条消息，只表示这条消息不进入本次 Agent 输入；原始聊天、文件、Git、数据库和项目记忆不会因此被删除或回滚。

## 2. 为什么需要它

如果每次提问都自动带上全部聊天记录，会出现几个问题：

- 今天的工作会被昨天和更早的讨论干扰；
- 已经废弃的方案可能继续影响 Agent；
- 上下文越来越长，Token 成本和延迟增加；
- 用户不知道 Agent 到底看到了哪些内容；
- 一次回答很难解释是依据了哪段历史；
- 不同任务的聊天内容混在一起，容易产生错误关联。

但如果完全不保留历史，又会出现另一个问题：用户取消了之前的消息后，Agent 可能不知道“登录页已经完成”“数据库迁移已经执行”或“Vue 方案已经确定”。

因此产品同时提供：

1. **按天隔离**：今天默认是新的聊天上下文；
2. **按需回溯**：需要昨天内容时，用户主动选择；
3. **状态提示**：提醒用户取消后 Agent 可能缺少哪些已完成事项；
4. **上下文快照**：发送前明确记录本次 Agent 实际使用的内容。

## 3. 最核心的产品原则

### 3.1 今天和昨天默认分开

上下文管理器按照项目所在时区划分日期。每天零点之后，默认进入新的“今日上下文”。

例如今天是 2026 年 9 月 20 日：

~~~text
默认可见并选中：2026-09-20 今天的聊天
默认不加入：2026-09-19 昨天的聊天
默认不加入：更早日期的聊天
~~~

同一个飞书私聊或项目群可以继续存在，但上下文管理器不会因为它们属于同一个聊天窗口，就自动把昨天的原始消息带入今天。

### 3.2 历史需要主动选择

如果用户需要昨天的信息，必须在卡片中点击“选择历史”，再选择日期、摘要、具体消息或相关状态。

选择历史是“把它加入本次上下文”，不是把昨天的聊天搬到今天，也不是修改历史归属日期。

### 3.3 用户控制详细历史，系统保护任务连续性

用户可以取消详细历史，但系统要提醒他取消后 Agent 可能不知道哪些事情已经完成。

系统不能偷偷把用户取消的普通历史重新塞回 Prompt，也不能让 Agent 根据未提供的历史进行猜测。它应该通过状态摘要和完整性提醒帮助用户做决定。

### 3.4 选择不等于删除

取消一条昨天的聊天、不选择某个摘要、不加入当前 Git diff，均只影响本次 Agent 输入，不会改变：

- 飞书原始聊天记录；
- 项目文件和 Git 分支；
- 数据库和 API 数据；
- Evidence；
- 已审批的 ProjectMemory；
- 之前的 AgentRun 和审计记录。

## 4. 用户看到的四类内容

上下文管理器把候选内容分成四类，不能混在一个“历史消息”列表里。

| 类型 | 它是什么 | 示例 | 本次取消后的影响 |
| --- | --- | --- | --- |
| 对话历史 | 用户和 Agent 原始说过的话 | “登录页已经完成” | 本次不提供给 Agent，原始聊天仍保留 |
| 外部状态 | 模型之外真实存在的状态 | 文件、Git diff、数据库结果 | 本次不带入，不改变真实状态 |
| 派生信息 | 从对话或外部状态整理出的内容 | 摘要、任务状态、运行摘要、项目记忆 | 本次不注入，不自动失效 |
| 上下文快照 | 一次发送前冻结的内容组合 | Snapshot 12 | 发送后不可修改，只能创建新的快照 |

特别需要区分：

~~~text
src/login.vue 文件本身       = 外部状态
这次读取到的文件内容         = 可以加入上下文的外部状态结果
“登录页已经完成”的摘要       = 派生信息
~~~

## 5. 按天隔离的上下文结构

### 5.1 今日上下文

这是默认工作区，包含当天的聊天记录和当天产生的相关 Agent 运行信息。

~~~text
今日：2026-09-20
- 今日用户问题
- 今日 Agent 回复
- 今日确认的任务状态
- 今日读取并允许使用的证据
~~~

今日内容默认进入候选列表，并按照当前任务给出推荐选择。

### 5.2 历史上下文

这是按日期查看的历史区域。昨天及更早的内容默认不加入本次快照，只有用户主动选择后才加入。

用户可以先选择一个日期，再选择该日期的原始消息、会话摘要、任务进展、某次运行摘要或相关证据。

### 5.3 跨日工作状态

跨日工作状态不是昨天的原始聊天，而是对“之前做到哪里”的结构化表达：

~~~text
跨日工作状态
- 登录页：已完成
- 订单列表：未开始
- 最近一次提交：abc123
- 下一步：实现订单管理
- 来源：2026-09-19 运行摘要
~~~

它可以比完整历史更省 Token，但必须显示来源日期、生成或确认时间、当前有效性，以及是否有 Evidence 或运行结果支持。它是推荐项，不是今天的原始聊天。

## 6. 摘要在产品中的位置

模型进行上下文压缩时，通常会把较早的一部分对话整理成摘要。摘要来自历史，但不是历史本身。

~~~text
原始消息 H1：电商后台使用 Vue
原始消息 H2：登录页面已经完成
原始消息 H3：下一步做订单管理

派生摘要 S1：项目使用 Vue，登录页已完成，下一步实现订单管理。
~~~

在卡片中应分开显示“今日聊天”“历史聊天”和“历史摘要”。摘要至少显示标题、短预览、来源日期、覆盖范围（如果可准确记录）、生成时间、估算 Token 和状态。

如果系统暂时不能准确记录摘要对应的每条历史消息，就只能显示“覆盖某次压缩周期”，不能假装提供精确来源关系。

## 7. 飞书中的交互方式

上下文管理器使用飞书原生互动卡片，不需要独立 Web 页面。

### 7.1 入口与今日卡片

用户在飞书中提问后点击“编辑本次上下文”。卡片顶部展示日期、默认范围、已选择数量和估算 Token。

~~~text
本次上下文
日期：2026-09-20
默认范围：今天
已选择：6 项
估算 Token：3,820 / 16,000

今日聊天 · 2026-09-20
[x] 订单管理需求确认       420 tokens
[x] 当前接口排查           260 tokens
[x] 今日任务状态           180 tokens

跨日状态（可选）
[ ] 昨日任务摘要           320 tokens
    昨日完成：登录页
    来源：2026-09-19

[选择历史日期] [预览上下文]
~~~

### 7.2 历史日期卡片

点击“选择历史日期”后，先展示日期列表，再分页展示某天的消息和摘要：

~~~text
选择历史
[2026-09-19 昨天]
[2026-09-18 2 天前]
[2026-09-17 3 天前]
~~~

~~~text
2026-09-19 · 昨天
[ ] Vue 技术选型             180 tokens
[ ] 登录页完成记录           290 tokens
[ ] 昨日会话摘要             320 tokens

[上一页] [下一页] [加入已选]
~~~

### 7.3 预览与完整性提醒

预览卡片展示 Agent 本次将看到的内容类别、日期来源和 Token：

~~~text
本次 Agent 将看到
- 今日聊天：2 项
- 历史聊天：1 项，来源 2026-09-19
- 摘要：1 项
- 任务状态：1 项
- Evidence：2 项
- 估算 Token：4,812 / 16,000

[发送给 Agent] [返回修改]
~~~

如果用户取消了可能包含关键完成状态的内容，发送前显示：

~~~text
可能缺少之前的工作状态

当前问题：继续实现订单管理
检测到：本次未选择“登录页已完成”的历史、摘要或任务状态

Agent 可能无法确认登录页是否已经完成。

[加入昨日任务摘要]
[加入相关历史]
[仍然发送]
~~~

“仍然发送”是用户明确做出的选择，不会偷偷补充内容；本次快照应记录用户忽略了完整性提醒。

### 7.4 群聊中的 @ 与非@消息

群聊里需要把“触发机器人”和“帮助机器人理解背景”分成两个动作：

- **@机器人消息**：表示用户现在希望机器人响应；`@` 后面的文本是本次问题或任务的明确锚点；
- **非@消息**：默认只是群聊历史，不单独触发 Agent，也不会自动全部进入本次 Prompt。

这里的 @ 规则只针对群聊。飞书私聊本身就是明确的对话入口，不要求用户额外 @ 机器人；私聊消息仍然要经过现有项目路由和上下文选择流程。

例如：

~~~text
张三：登录页已经完成了
李四：那订单列表接口是不是也要一起改？
王五：订单状态还需要产品确认
李四：@ProjectLens 请总结一下现在订单管理的进展和下一步
~~~

机器人应把最后一条 `@` 消息识别为当前任务；前面三条非@消息只是候选背景，不是已经自动确认的上下文。候选范围按以下优先级处理：

1. 当前 `@` 消息本身；
2. `@` 消息所在 thread 的父消息和回复；
3. 同一 thread 附近的有限时间窗口内消息；
4. 今天同一群聊中与当前问题语义相关的非@消息；
5. 用户主动选择的昨天及更早历史。

更早日期的消息不能因为当前 `@` 就自动加入，仍需通过“继续昨天工作”或“选择历史”主动选择；无关闲聊也不能仅因为落在时间窗口内就进入快照。

#### 机器人如何理解群聊“重点”

机器人不应该把最近几十条群聊原样塞进 Prompt，而应采用“确定性筛选 + 模型提炼 + 用户确认”的流程：

~~~text
收到群聊事件
-> 判断是否真的 @ 了机器人
-> 提取 @ 后文本作为当前任务
-> 读取 thread 父消息和回复
-> 在权限范围内筛选有限时间窗口
-> 推荐当天语义相关的非@消息
-> 生成“我理解的重点”
-> 用户确认或编辑选择
-> 冻结本次上下文快照
-> 发送给 Agent
~~~

“我理解的重点”必须能回指到原始消息，至少显示来源人、时间、消息或 thread 标识、相关性理由和是否被用户确认。飞书卡片提供三个入口：

- **直接回答**：使用推荐且通过权限检查的候选创建快照；
- **编辑上下文**：进入现有三种模式和候选编辑流程；
- **选择更多历史**：打开按日期选择界面。

#### @ 不扩大权限

`@机器人` 只是触发器和任务锚点，不是权限授权。机器人仍然只能读取当前用户、当前群聊和当前 ProjectSpace 允许看到的内容。发送者身份必须从 Feishu 可信事件解析；非@消息即使语义相关，也必须经过群聊可见性和 EffectiveAccessScope 检查；无法确认 mention 元数据时，应按普通消息记录，不能猜测用户在召唤机器人。

## 8. 一次完整的使用示例

### 8.1 第一天

2026-09-19，用户和 Agent 讨论登录页和订单管理，系统形成摘要：

~~~text
S1：项目使用 Vue，登录页已完成，下一步实现订单管理。
~~~

### 8.2 第二天默认状态

2026-09-20，用户打开同一个飞书项目群并问“开始实现订单管理”。上下文管理器默认只使用 2026-09-20 的今日上下文，昨天的原始消息和摘要显示为可选历史，不自动加入。

### 8.3 用户主动回溯

用户选择昨日摘要 S1，生成的本次快照是：

~~~text
Snapshot 12
- 今日问题：开始实现订单管理
- 昨日摘要 S1
- 当前项目和权限边界
- 估算 Token：1,180
~~~

用户不必把昨天全部消息重新加入，只补充与今天任务有关的状态即可。

### 8.4 用户保持今天独立

如果用户不选择 S1，系统提示 Agent 不会知道登录页是否已完成。用户仍然可以发送探索性问题，但 Agent 必须先读取当前项目状态，或明确说无法确认。

## 9. 上下文完整性与 Agent 边界

完整性提醒用于回答：“按当前选择，Agent 是否可能不知道继续工作所需的已完成事项？”

典型情况包括：

- 当前问题是“继续实现”，但没有选择任务状态；
- 用户要修改已有功能，但没有选择最近运行摘要或相关 Evidence；
- 用户选择了今天的后续消息，却没有选择它依赖的前置背景；
- 用户取消了覆盖“已完成事项”的摘要。

提醒分为三类：信息提示、需要确认的警告、权限失效/来源撤销/超预算等硬阻断。

如果某个事实没有进入本次快照，Agent 不应把它当作已知事实，而应该明确说：

~~~text
根据本次提供的上下文，我无法确认登录页是否已经完成。
你可以让我读取当前项目状态，或加入昨天的任务摘要后再继续。
~~~

## 10. 第一优先级核心功能

以下六项组成上下文管理器的第一版核心体验。它们共同回答三个问题：今天默认使用什么、如何继续之前的工作、这次 Agent 到底看到了什么。

### 10.1 继续昨天工作

这是跨日使用的快捷入口。每天第一次打开上下文管理器时，飞书卡片提供：

~~~text
开始今天的工作

今天的上下文已经准备好。

[今日专注]
只使用今天的聊天

[继续昨天的工作]
加入昨日工作交接摘要和未完成事项

[历史调查]
选择指定日期和详细消息
~~~

点击“继续昨天的工作”后，系统不会把昨天所有原始消息全部加入，而是先推荐低 Token、高价值的跨日信息：

- 昨日工作交接摘要；
- 昨日未完成事项；
- 昨日最后一次已验证运行摘要；
- 昨日确认的关键决策；
- 与今天问题直接相关的 Evidence。

用户可以直接接受推荐，也可以展开后逐项取消或补充原始历史。

这个功能的目的不是让今天和昨天重新变成一个无限增长的聊天，而是提供一个受控的“工作接力”。

### 10.2 三种上下文模式

用户不必每次从零勾选内容。上下文管理器提供三个入口模式：

| 模式 | 默认内容 | 适合场景 |
| --- | --- | --- |
| **今日专注** | 今天的聊天、今天的任务状态和当前问题 | 开始一个新问题，不希望过去讨论干扰判断 |
| **继续工作** | 今天的内容 + 昨日工作交接摘要 + 未完成事项 | 接着昨天的任务继续推进 |
| **历史调查** | 今天的内容 + 用户指定日期、消息、摘要或证据 | 追溯决策、排查事故、核对历史争议 |

模式只是选择起点，不是权限边界。用户进入模式后仍可以调整具体项目；所有模式都要经过同样的权限检查、Token 检查和完整性提醒。

### 10.3 每日工作交接摘要

每日工作交接摘要是跨日连续性的核心对象。它不是昨天聊天的复制品，而是对“昨天做到哪里”的结构化说明。

建议包含：

~~~text
昨日工作交接 · 2026-09-19
- 当前目标：实现订单管理
- 已完成：登录页、用户认证接口
- 进行中：订单列表 API
- 未完成：订单详情和状态更新
- 已确认决策：前端使用 Vue
- 未解决问题：支付状态字段仍待产品确认
- 下一步：补充订单列表分页
- 来源：昨日会话摘要、AgentRun、Git 状态、Evidence
~~~

用户可以把它作为一个整体加入今天的上下文，也可以展开为“已完成”“未完成”“决策”“待确认问题”分别选择。

交接摘要必须显示来源日期和生成时间。如果它已经过期、缺少证据或与最新外部状态冲突，卡片要标记相应状态，不能把它伪装成当前事实。

### 10.4 摘要与原始消息粒度选择

同一段历史可以有不同的上下文粒度。用户选择一段历史时，系统提供：

~~~text
昨日登录模块讨论

( ) 使用原始消息       1,850 tokens
( ) 仅使用摘要             320 tokens
( ) 摘要 + 关键原文        620 tokens
~~~

三种方式的含义是：

- **原始消息**：保留完整讨论过程，适合需要理解争论、决策原因和措辞的场景；
- **仅使用摘要**：只带入结论、当前状态和下一步，适合继续工作和控制 Token；
- **摘要 + 关键原文**：保留摘要，再加入用户标记的几条关键消息，兼顾背景和细节。

默认情况下，同一覆盖范围的摘要和原始消息不同时自动选中，避免重复占用上下文。用户明确选择两者时，系统只提示可能重复，不替用户强制删除。

摘要不是原始证据的替代品。涉及争议、责任、事故时间线或需要精确措辞时，系统应建议用户加入相关原文或 Evidence。

### 10.5 上下文完整性提醒

用户可以自由减少上下文，但减少后 Agent 可能不知道之前已经完成了什么。因此发送前需要检查当前选择是否缺少明显的任务连续性。

例如：

~~~text
当前问题：继续实现订单管理

可能缺少之前的工作状态：
- 未选择“登录页已完成”的历史、摘要或任务状态
- 未选择最近一次订单模块运行摘要

建议：
[加入昨日工作交接]
[加入相关运行摘要]
[仍然发送]
~~~

完整性提醒只做三件事：说明可能缺少什么、推荐可以加入什么、让用户明确决定是否继续。它不会偷偷把已取消的历史加入 Prompt，也不会因为普通信息缺失就阻止所有探索性问题。

只有权限失效、来源撤销、内容版本变化或 Token 超预算等硬错误才强制阻止发送。用户选择“仍然发送”后，快照记录本次忽略了哪些提醒；Agent 必须对未提供的事实明确表示无法确认。

### 10.6 上下文快照回看

每次发送都会生成一个不可变的上下文快照。用户可以在飞书中点击“查看本次上下文”，看到：

~~~text
Snapshot 12 · 2026-09-20 10:42

本次使用：
- 今日聊天：2 项
- 昨日交接摘要：1 项，来源 2026-09-19
- 原始历史：0 项
- Evidence：2 项
- 任务状态：1 项

Token：4,812 / 16,000
完整性提醒：1 条，用户选择继续发送
状态：AgentRun 已完成

[查看摘要] [查看运行结果]
~~~

回看功能至少要让用户知道：

- 本次使用了哪些日期的内容；
- 使用了摘要还是原始消息；
- 哪些内容被用户取消；
- 当时的 Token 估算；
- 是否出现完整性提醒；
- AgentRun 是否成功；
- 本次快照与哪次回答关联。

快照回看不是恢复或编辑历史。用户想修改输入时，应复制为新的选择，再生成新的快照。

### 10.7 群聊重点捕获（配套能力）

群聊重点捕获不改变六项核心上下文功能，只负责把群聊中的自然讨论转成一次可编辑的 Context Draft：

1. 非@消息持续保存为当天群聊历史，但不启动 AgentRun；
2. `@机器人` 消息启动 Context Draft，而不是直接把整个群聊发送给 Agent；
3. 当前 @ 文本始终作为问题锚点，不能被模型摘要替换；
4. thread 和有限时间窗口内的相关非@消息显示为推荐候选；
5. 推荐候选展示来源人、时间、消息 ID 或 thread 信息；
6. 用户确认后才进入不可变 Snapshot；
7. 昨天及更早消息仍需主动选择；
8. Agent 只能知道进入 Snapshot 的内容，不能根据未选消息猜测重点。

## 11. 其他基础功能

1. **今日聊天默认隔离**：每天形成新的默认上下文分区。
2. **历史按日期查看**：昨天及更早内容不自动混入，可按日期查找。
3. **按片段选择历史**：可以选单条消息、消息组、摘要或运行摘要。
4. **摘要可视化**：展示来源日期、覆盖范围、生成时间、Token 和状态。
5. **跨日状态提示**：提醒用户之前完成了什么，以及是否需要加入。
6. **Token 预算预览**：显示本次选择的大致上下文成本。
7. **Prompt 预览**：发送前查看 Agent 将看到哪些内容。
8. **不可变上下文快照**：保存本次 Agent 实际使用的内容组合。
9. **缺失上下文提醒**：发现任务连续性风险时给出建议，但不偷偷补回历史。
10. **历史与真实状态分离**：选择操作不删除聊天，不修改 Git、文件、数据库或项目记忆。
11. **群聊重点捕获**：非@消息保存为候选背景，@机器人消息触发重点确认，不自动读取整个群聊。

## 12. 明确不做什么

当前产品不做：

- 不把所有日期的聊天自动合并；
- 不因为今天开始了新上下文就删除昨天的聊天；
- 不因为用户取消消息就回滚之前的代码或数据库操作；
- 不在用户取消历史时自动重建摘要或长期记忆；
- 不让 Agent 访问未被本次选择且没有经过授权的历史；
- 不把用户选择当成修改真实项目状态的操作；
- 不用一张卡片塞进无限数量的聊天记录，超出范围时按日期和分页查看。

## 13. 用户如何理解几个词

| 词语 | 用户可以理解为 |
| --- | --- |
| 今日上下文 | 今天默认给 Agent 看的工作内容 |
| 历史上下文 | 用户主动补充进本次问题的过去内容 |
| 摘要 | 对一段较长聊天的压缩说明，不是原始聊天本身 |
| 工作状态 | 已完成、进行中、下一步等对继续工作有帮助的信息 |
| Evidence | 支持某个事实的外部依据 |
| 本次快照 | 发送时冻结的“Agent 本次知道什么” |
| 完整性提醒 | 系统发现 Agent 可能缺少前置背景时的提示 |

## 14. 产品成功标准

用户使用后应该能够清楚回答：

1. 今天的 Agent 为什么没有看到昨天的消息？
2. 我怎样把昨天的一条摘要加入今天的问题？
3. Agent 本次到底看到了哪些内容？
4. 我取消一条历史会不会删除真实数据？
5. 如果我取消了“登录页已完成”，Agent 会不会知道？
6. 为什么系统提醒我可能缺少上下文？

设计目标成立的标志是：默认使用今天的聊天；用户可以按日期主动加入历史；摘要和原始聊天明确区分；跨日完成状态有来源和日期；取消历史不会修改真实项目状态；Agent 不会把未进入快照的信息假装成已知事实；每次发送都可以回看本次快照。

## 15. 最终产品原则

> **上下文管理器按天隔离聊天，按需允许历史回溯；用户可以决定 Agent 本次看到哪些详细历史，但系统必须提醒他取消后 Agent 可能不知道哪些事情已经完成。系统不能偷偷注入内容，也不能让 Agent 对缺失信息进行猜测。**

在群聊场景中，这条原则进一步具体化为：

> **@机器人表示用户希望现在得到响应，但不代表机器人应该读取整个群聊。非@消息只有在与当前 @ 任务在线程、时间和语义上相关，并且通过权限检查后，才可作为本次上下文候选；机器人应先展示它理解的重点和依据，再生成最终回答。**
