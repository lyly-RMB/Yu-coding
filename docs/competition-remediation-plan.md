# ProjectLens 参赛整改与交付计划

**版本**：V1.0  
**日期**：2026-10-10  
**目的**：把当前 ProjectLens 从“技术能力较完整的研发系统”收敛为“可稳定演示、可量化验证、可提交评审的软件产品”。

## 1. 结论摘要

当前项目的主要风险不在于功能数量不足，而在于以下三点：

1. 核心飞书协作闭环还没有完成一轮无阻断的真实回归。
2. 检索和上下文评测数据量不足，现有报告仍为 `insufficient_data`。
3. 产品范围较宽，缺少面向评委的单一主场景、演示视频和量化应用效果。

本计划的交付顺序是：

```text
修复稳定性
-> 完成真实回归
-> 扩充评测数据
-> 冻结发布版本
-> 完成比赛材料和演示
-> 进行小规模试点并量化价值
```

在 P1 缺陷关闭、核心剧本完整通过之前，不应对外宣称产品已经通过验收或适合正式试运行。

## 3. 优先级定义

| 优先级 | 含义 | 处理要求 |
|---|---|---|
| P0 | 无法运行、数据泄露或无法演示 | 立即阻断发布 |
| P1 | 核心场景结果不正确或真实链路不稳定 | 比赛提交前必须关闭 |
| P2 | 次要功能、数据质量或可维护性问题 | 提交前解决或明确披露 |
| P3 | 体验、记录和材料完整性问题 | 在最终包装阶段解决 |

## 4. 问题与解决方案

### R-01：核心飞书闭环尚未完成验收（P1）

**问题**：现有质量报告显示剧本一在干预总结处因多角色上下文不连续而中止，剧本二、剧本三以及部分恢复、幂等和权限场景未覆盖。

**解决方法**：

1. 确认群聊会话按 `physical_actor_id + chat_id` 或群级会话保持连续。
2. `effective_actor_id` 只用于角色权限和回答视图，不用于拆分群聊上下文。
3. 重启 API，清理旧会话，从剧本一第一步重新开始，禁止从中断步骤续跑。
4. 完整执行需求变更、发布风险评审、决策记忆三套剧本。
5. 补测权限隔离、重复事件幂等、服务重启恢复和主动提醒边界。

**验收标准**：

- 三套核心剧本全部完成；
- P0/P1 缺陷为 0；
- 管理者可以基于同一群聊中的多角色发言生成准确总结；
- 同一事件重复投递不会产生重复回答或重复写入；
- API 重启后会话、审批和记忆状态可恢复；
- 测试报告明确记录输入、输出、Run ID、trace ID 和截图。

**交付物**：新的质量报告、执行日志、缺陷清单、关键步骤截图和最终通过结论。

### R-02：Hermes 和外部模型链路存在超时风险（P1）

**问题**：真实测试中曾出现 `HERMES_AGENT_LOOP_FAILED` 和 SSE 长时间无事件。模型、工具调用和飞书回复之间的超时边界仍需要真实验证。

**解决方法**：

1. 统一模型请求、SSE、工具调用和飞书最终回复的超时配置。
2. 为模型无响应、工具失败、网络断开和上下文超限分别定义错误状态。
3. 确保 fallback 到 Stub 或可理解的降级回复，不把错误伪装成业务结论。
4. 记录每次重试、fallback、耗时和最终状态。
5. 使用慢模型、断网、无效 API Key 等故障注入场景执行冒烟测试。

**验收标准**：

- 模型超时不会导致飞书无回复；
- 降级回复明确说明“未完成模型分析”，不生成无证据事实；
- 关键请求记录 p50、p95 延迟；
- fallback 成功率达到现有门禁要求 `1.0`；
- 连续 20 次真实或录制回放请求无未处理异常。

**交付物**：稳定性测试表、错误状态说明、延迟统计和失败回放日志。

### R-03：知识种子和来源完整性不足（P1/P2）

**问题**：测试前置资料曾缺少“支付失败重试两次”旧规则，导致冲突识别场景无法可靠建立基线。

**解决方法**：

1. 为每个演示项目建立必备资料清单，包括需求、会议、代码、任务、测试和发布记录。
2. 导入前执行来源完整性检查，缺失资料时阻止进入“通过”状态。
3. 为每条资料保留来源地址、版本、更新时间、有效期和权限范围。
4. 对过期、撤销、冲突和未确认资料分别标记，不允许静默覆盖。
5. 增加知识库新鲜度和冲突前置检查。

**验收标准**：

- 演示项目的必备资料全部存在并可追溯；
- 缺失资料会被报告为 `missing`，不会被解释为“没有冲突”；
- 旧规则与新规则同时存在时，回答明确展示时间和冲突状态；
- 无证据内容不得输出为已确认事实。

**交付物**：演示项目资料清单、导入检查报告、资料版本说明和冲突样例。

### R-04：检索与上下文评测数据不足（P1）

**问题**：当前检索集只有 12 条用例，上下文压缩集只有 2 条用例，报告因此无法作为充分的算法有效性证明。

**解决方法**：

1. 扩充至少 100 条锁定的检索黄金样例。
2. 扩充至少 50 条上下文压缩样例。
3. 覆盖项目介绍、状态查询、需求实现核对、会议结论、风险、冲突、知识缺口、过期事实、拒答、多轮上下文和权限隔离。
4. 为每条样例固定问题、允许证据、正确结论、禁止结论和权限范围。
5. 运行 lexical、vector、hybrid 三种模式对比，保留数据集哈希和 Git revision。

**建议验收指标**：

| 指标 | 目标 |
|---|---:|
| citation correctness | >= 0.95 |
| temporal correctness | >= 0.95 |
| conflict recall | >= 0.95 |
| abstention precision | >= 0.95 |
| fallback success rate | 1.0 |
| cross-scope leakage | 0 |
| revoked/expired misuse | 0 |

如果目标未达到，应在报告中如实披露，并说明后续优化计划，不应修改样本或隐藏失败结果。

**交付物**：锁定数据集、评测配置、三种检索对比报告、失败案例分析和最终门禁结论。

### R-05：产品范围过宽，主场景不够聚焦（P2）

**问题**：项目同时包含问答、记忆、风险、上下文压缩、知识缺口、MCP、多项目和多个连接器，评委不容易快速理解产品价值。

**解决方法**：

将参赛版本固定为一个主场景：

> 支付失败重试次数从 2 次改为 3 次，ProjectLens 在飞书群聊中分析需求、会议、代码、测试和发布影响。

演示固定为：

```text
提问
-> 多来源检索
-> 证据化回答
-> 冲突/未知识别
-> 影响、风险和负责人
-> 人工确认
-> 项目记忆更新
-> 再次提问验证闭环
```

其它能力只作为支撑，不在首屏逐项展开。

**验收标准**：评委在 90 秒内能说出产品是什么、服务谁、解决什么问题；5 分钟内能看完一个完整闭环。

**交付物**：一句话定位、主流程图、演示脚本和功能取舍表。

### R-06：产品体验和评委上手路径偏弱（P2）

**问题**：当前主要入口是飞书群聊、API 文档和脚本。若评委无法接入飞书环境，产品体验和证据查看会受影响。

**解决方法**：

1. 准备一个可复现的本地录制模式，不依赖真实飞书账号也能回放主流程。
2. 提供预置项目、预置账号、预置问题和一键启动说明。
3. 在回答中突出结论、影响、冲突、未知、下一步和来源。
4. 确保 Run ID、Evidence 和审计入口可快速定位。
5. 如时间允许，提供只读的项目状态、风险、知识缺口和运行记录页面；不为比赛临时引入复杂前端。

**验收标准**：新机器按部署手册可在 15 分钟内启动；评委可在无真实模型 Key 时使用录制/Stub 模式完成体验；每个关键结论都能展开来源。

**交付物**：一键启动脚本、演示账号说明、离线回放数据、截图和操作手册。

### R-07：发布版本和研发工作区尚未冻结（P2）

**问题**：当前工作区包含大量修改、删除和新增文件，仍处于持续重构和迁移状态，存在代码、文档和配置不一致风险。

**解决方法**：

1. 完成 R-01 至 R-04 后建立 release 分支或 release tag。
2. 在全新虚拟环境安装依赖，不依赖本机残留环境。
3. 运行完整测试、编译检查、格式检查和启动检查。
4. 清理不应交付的数据库、日志、临时配置和密钥文件。
5. 固定 `.env.example`、演示数据、模型配置和数据库初始化步骤。

**验收标准**：全新目录能够按照 README 完成安装、启动、健康检查和主流程回放；同一 commit 可重复生成测试报告。

**交付物**：release commit、版本说明、依赖清单、部署包或镜像、变更记录。

### R-08：安全与合规证据不足（P1/P2）

**问题**：代码已有权限、ProjectSpace 和服务令牌设计，但参赛材料还缺少可验证的安全边界和数据处理说明。

**解决方法**：

1. 固定“权限在检索前生效”的流程，并补充跨项目、跨角色、撤销权限和过期资料测试。
2. 检查模型请求、日志、截图和测试数据中是否包含真实密钥或敏感信息。
3. 说明飞书数据、模型输入、数据库和日志的保存位置、保留周期和删除方式。
4. 保持自动改代码、自动部署、自动回滚和无审批记忆写入关闭。
5. 将越权尝试、拒答和审计记录纳入演示或测试报告。

**验收标准**：跨项目和跨角色泄露次数为 0；撤销权限后不能读取受限内容；所有正式记忆写入都有审批记录；仓库不包含真实密钥。

**交付物**：安全边界说明、权限测试报告、数据处理说明和脱敏检查结果。

### R-09：应用价值没有量化（P2）

**问题**：当前有较完整的产品目标，但缺少实际试点数据，应用价值主要停留在设计层面。

**解决方法**：

1. 选择一个项目、2-5 名测试者，覆盖产品、研发、测试和负责人角色。
2. 连续使用 5-7 天，记录问题类型、使用次数、响应时间、引用质量和人工纠正。
3. 记录使用 ProjectLens 前后的资料查找耗时。
4. 统计发现的冲突、知识缺口、风险和待确认事项。
5. 对所有数据注明样本量、时间范围和测试环境。

**建议记录指标**：

- 带证据回答率；
- 未知/冲突识别准确率；
- 权限越界次数；
- 平均和 P95 响应时间；
- 单次问题平均查找耗时；
- 用户纠正率和满意度；
- 发现并闭环的知识缺口数量。

**交付物**：试点记录表、匿名化统计图、用户反馈摘要和局限性说明。

### R-10：比赛提交材料不完整（P2/P3）

**问题**：当前研发文档很多，但尚未形成面向评审的独立材料包。

**解决方法**：

新建 `competition/` 或参赛材料目录，至少准备：

```text
技术方案书.md
软件说明书.md
核心算法说明.md
测试报告.md
部署手册.md
演示脚本.md
答辩PPT大纲.md
assets/
  architecture.png
  workflow.png
  screenshots/
  demo-video.mp4
```

技术方案书按比赛给出的五部分组织：产品定位、技术架构与创新、功能设计与实现、开发测试与部署、应用价值与展望。

**验收标准**：评委不阅读内部研发规划，也能独立理解产品、运行产品、验证核心功能并查看测试证据。

## 5. 推荐执行顺序

### 阶段 A：稳定性清零

- 完成 R-01 多角色会话和飞书三套剧本回归；
- 完成 R-02 Hermes 超时、错误和 fallback 测试；
- 修复所有 P0/P1；
- 生成新的真实测试报告。

### 阶段 B：数据与算法验收

- 完成 R-03 演示知识库完整性；
- 扩充 R-04 检索和上下文数据集；
- 运行安全、时间有效性、引用和冲突评测；
- 记录失败样例和优化前后对比。

### 阶段 C：产品冻结

- 完成 R-05 主场景收敛；
- 完成 R-06 评委上手路径；
- 完成 R-07 release 版本和全新环境部署；
- 冻结演示数据和演示脚本。

### 阶段 D：比赛包装与试点

- 完成 R-08 安全合规材料；
- 完成 R-09 小规模试点和效果数据；
- 完成 R-10 技术方案、说明书、测试报告和视频；
- 进行一次完整答辩彩排。

## 6. 最终发布门槛

满足以下条件后，才建议提交参赛版本：

- [ ] 核心飞书剧本全部完成；
- [ ] P0/P1 缺陷为 0；
- [ ] 模型超时和 fallback 已验证；
- [ ] 演示资料完整且可追溯；
- [ ] 检索集不少于 100 条；
- [ ] 上下文压缩集不少于 50 条；
- [ ] 权限越界为 0；
- [ ] 全新环境可以部署和回放；
- [ ] 有一组真实或明确标注的内部试点数据；
- [ ] 软件说明书、核心算法说明、测试报告和演示视频齐全；
- [ ] 参赛版本已打 tag，代码、配置、文档和报告对应同一版本。

## 7. 不建议当前阶段继续做的事情

- 不要继续增加新的连接器；
- 不要在发布前扩展复杂 GraphRAG；
- 不要新增自动改代码、自动部署或自动回滚能力；
- 不要用更多概念替代主场景演示；
- 不要把仍含 P1 或 `insufficient_data` 的报告当作最终验收材料；
- 不要把未经脱敏的 `.env`、数据库、日志或真实飞书数据打包提交。
